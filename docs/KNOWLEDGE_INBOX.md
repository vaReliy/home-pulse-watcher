## 2026-09-12 — gcloud describe fail-open pattern is unsafe for destructive-action guards

Why: implementing the api-runtime-sa migration guard (`scripts/gcloud-bootstrap.sh`), first draft used `CURRENT_SA=$(gcloud run services describe ... 2>/dev/null || echo "")` to detect "service not deployed yet" before allowing an IAM revoke. This conflates "service absent" with "describe call errored for any reason" (expired auth, wrong active project, API not enabled, network blip) — both yield empty string, so an errored check on a live prod service silently fell through to "safe to revoke." Reviewer caught it; fix separates existence check (`if gcloud ... &>/dev/null; then`) from the value fetch, matching the pattern already used 3x elsewhere in the same file (~lines 459/468/491). Also: `spec.template.spec.serviceAccountName` comes back empty for a service running under the implicit default compute SA (no explicit --service-account ever set) — must not treat empty-but-exists the same as "safe," map it to the known legacy SA instead.

Belongs in (guess): `rules/local/shell-scripting.md` — general rule: any bash guard gating a destructive/irreversible action (IAM revoke, delete, etc.) must fail closed on command error, never fold "command failed" into the same branch as "expected empty/absent state." Existence checks and value fetches must be separate calls/branches.

## 2026-09-12 — platformio.ini section-scoped parsing must anchor headings to line-start

Why: fixing `test_esp32c3_dev_env_disables_tls`/`test_esp32c6_dev_env_disables_tls` (`libs/firmware-shared/test/test_transport_security/test_transport_security.cpp`) to scope their `-DHPW_USE_TLS=0` check to the `[env:esp32c3_dev]`/`[env:esp32c6_dev]` section instead of whole-file search. `firmware/esp32c3/platformio.ini` and `firmware/esp32c6/platformio.ini` have prose comments above sections that mention the _next_ section heading by name (e.g. `; ... see [env:esp32c3_dev] below ...`) before the real heading line — a plain `std::string::find(ini, "[env:esp32c3_dev]")` latches onto that comment first and extracts the wrong slice. New `extractEnvSection()` helper requires the heading match be preceded by `\n` or be at offset 0 (i.e. actually starts a line). Also noted: the pre-existing sibling `_release` tests do NOT use any section-scoping helper (still whole-file `contains(ini, "-DHPW_USE_TLS=1")`) — a prior task file incorrectly assumed they did; they may deserve the same fix as a follow-up.

Belongs in (guess): `libs/firmware-shared` test-writing conventions (rule or comment near the helper) — any future platformio.ini section-scoped test parsing must reuse `extractEnvSection` or its anchoring approach, not re-derive a naive `find`.

## 2026-09-12 — Debug-log PII redaction: fix at call site, do not trust log-level default

Why: auditing `logger.debug()` calls for PII leaks (`apps/api/src/modules/telegram/telegram.controller.ts` logged raw Telegram message text), found the repo has no `LOG_LEVEL` env var and no explicit `level` in the main API's `pinoHttp` config (`app.module.ts`) — Pino defaults to `info`, so `.debug()` never emits today. Chose redaction (log `textLength` instead of raw text) over an opt-in env-var gate, since adding new env-var infra just to gate one log line would be dead weight when the default already suppresses it — but redaction is still correct because the default is one config line away from being flipped to `debug`, and a future dev flipping it for troubleshooting must not accidentally leak PII. Separately, `apps/api/src/cli/cli.module.ts:28` sets its own `LoggerModule.forRoot({ pinoHttp: { level: 'warn' } })`, independent of the API app's config — worth checking both if auditing log levels again.

Belongs in (guess): `PROJECT_CONTEXT.md`'s Structured Logging section (already got a related note this session) — the general principle ("redact PII at the log call site, never rely on log-level defaults as a security boundary") could also become a short line in `rules/cts/validation-authorization.md` or a security rule if a second occurrence shows up.

## 2026-09-12 — docker-compose postgres volume keeps stale password across restarts without -v

Why: implementing the `boardType`-on-`Device` migration, local `prisma migrate dev` failed with `P1000: password authentication failed` against localhost:5432. Root cause: the `home-pulse-watcher_postgres_data` docker volume persists across `docker compose down` (without `-v`), so `POSTGRES_PASSWORD` only takes effect on first initdb — restarting with a different `DB_PASSWORD` against an existing volume silently keeps the old password baked into the volume, producing a misleading auth-failure error rather than any volume-mismatch signal. Fix: `docker compose down -v postgres \&\& DB_PASSWORD=<anything> docker compose up -d postgres` gives a clean known-credential local DB (safe for local/dev only — throwaway data, not prod).

Belongs in (guess): a short note near the local Docker/Postgres setup instructions (README or `rules/local/docker-commands.md`) so future agents dont waste a debug cycle assuming DB auth failure means wrong `.env` value.

## 2026-09-12 — Presence-check and extraction must share one line-start-anchored call, not two mismatched matchers

Why: closing the gap flagged in the entry above — the `_release` env tests (`test_esp32c3_release_env_enables_tls`, `test_esp32c6_release_env_enables_tls`) and, it turned out, the `_dev` tests too, still ran a separate whole-file `contains(ini, "[env:...]")` presence assert before calling the line-start-anchored `extractEnvSection()`. Two different matchers checking "does this section exist" can silently diverge: the naive `contains()` would false-pass on a prose-only mention even though `extractEnvSection()` (correctly) wouldn't find a real heading line, producing a misleading downstream failure message instead of "heading not found." Fixed by calling `extractEnvSection()` once and asserting `!section.empty()` for presence, reusing the same result for the content assert — general pattern: when a helper's return value already encodes "not found," never gate presence with a second, differently-scoped matcher.

Belongs in (guess): same home as the entry above (`libs/firmware-shared` test-writing conventions) — could be merged into one entry when distilled.

## Deferred / sub-floor
