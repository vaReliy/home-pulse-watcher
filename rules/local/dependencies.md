## Extends rules/cts/dependencies.md — new section: Root-Range/Exact-Pin Drift Nests a Duplicate Dep

An app-level exact pin mismatched from root's resolved range nests a duplicate dependency. `apps/api/package.json` exact-pinned `"rxjs": "7.8.0"` while root `package.json`'s `"^7.8.0"` range resolved to `7.8.2` (pulled in by other deps). Since apps/api's exact pin wasn't satisfied by the hoisted `7.8.2`, npm silently nested a second `rxjs@7.8.0` under `apps/api/node_modules` instead of erroring — no warning, no lockfile conflict message. Two copies of `rxjs` in the module graph meant two distinct `Observable`/`Subscriber` classes at the type level, which `tsc` reported as unrelated protected-member (`isStopped`) structural-typing errors in `bigint-serializer.interceptor.ts` that looked like an interceptor bug, not a dependency issue. This persisted across a forced `tsc -b --force` rebuild, which is what distinguishes it from a stale `.tsbuildinfo` cache artifact.

**Diagnostic**: compare `<pkg>/package.json` version fields between root `node_modules` and the nested app's `node_modules` directly, not just the declared ranges in each `package.json`.

**Fix**: align the app's exact pin to root's actually-resolved version, then regenerate the lockfile — never hand-delete the nested folder, it regenerates on next `npm install`. This was fixed by pinning to `7.8.2`; the issue is resolved, not open.

**Secondary symptom worth knowing**: with `tsconfig.base.json`'s `noEmitOnError: true`, this class of bug (one unrelated file failing type-check) blocks `.d.ts` re-emission for the _entire_ project under `tsc --build` mode once `out-tsc/*.tsbuildinfo` goes stale — any newly-added file then reports `TS6305: output file has not been built from source` instead of its real errors (or no error at all), and the false signal persists silently since the incremental cache never gets a clean chance to rebuild. Workaround when hit: run `npx tsc -p <app>/tsconfig.app.json --noEmitOnError false` once to force full `.d.ts` re-emission, then verify new/changed files add zero _new_ errors via `tsc --noEmit` directly against `tsconfig.app.json`/`tsconfig.spec.json` — this bypasses `--build` mode's incremental-cache confusion entirely.

## Extends rules/cts/dependencies.md — new section: Periodic Full-Workspace Pin Cross-Diff

Root-range/exact-pin drift generalizes beyond a single package: a repo-wide `^`/`~` audit that exact-pins every root range must also cross-diff each pin against workspace members' pins — not just check both sides are "exact," but that they match root's _newly resolved_ version. Found `reflect-metadata` stale in `apps/api/package.json` (`0.1.13` vs. root's resolved `0.1.14`) and `tslib` stale across `apps/api` + all 4 `libs/*/package.json` (pinned/ranged at `2.3.0` vs. root's resolved `2.8.1`) — same drift class as the rxjs incident above, just not yet triggering a visible `tsc` error. Root's un-pinned range let npm silently advance the hoisted version over time while workspace members' exact pins never got bumped; two exact pins can still mismatch each other.

This drift accumulates silently with no build error until a `tsc`/type-identity failure surfaces it, so a periodic full-workspace grep+cross-diff step is needed — not just a one-time post-generator audit.
