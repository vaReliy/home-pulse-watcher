## Overrides rules/cts/testing.md — test runner

This repo is pure Jest (`@nx/jest`, `ts-jest`/`@swc/jest` in every app/lib) — zero Vitest dependency in `package.json`. Where `rules/cts/testing.md` or the `vitest-testing` skill shows Vitest APIs (`vi.fn`, `vi.mock`, `vi.spyOn`, `vi.stubEnv`, import from `'vitest'`), use the Jest equivalents (`jest.fn`, `jest.mock`, `jest.spyOn`; `jest`/`describe`/`it`/`expect` are globals, no import needed) instead. Always invoke tests via `nx test <project>`, never `docker compose exec app npx vitest/jest` directly.

## Extends rules/cts/testing.md — new section: `SetMetadata`-Based Decorators Can Hide the Real Logic at the Call Site

`apps/api/src/decorators/hmac-canonical.decorator.ts` is a thin `SetMetadata` wrapper — the actual security-critical canonical-string-building logic lives as anonymous arrow functions at each `@HmacCanonical(...)` call site (`device-status.controller.ts`, `ota.controller.ts`), not in the decorator itself. A spec testing only decorator mechanics (metadata attach/retrieval) would miss the real logic entirely. Fix pattern: pull the live builder off the controller prototype via `new Reflector().get(HMAC_CANONICAL_KEY, Controller.prototype.method)` — the same lookup `HmacAuthGuard` does at request time — and exercise _that_ function, so the test tracks the production closure instead of a hand-copied duplicate that can silently drift. Applies to any future `SetMetadata`-based decorator whose payload is business logic rather than the decorator's own behavior.

## Extends rules/cts/testing.md — new section: Verifying a JSON Key Exists Is Not Verifying Its Value

A firmware test asserted `strstr(payload, "firmwareVersion")`, which passed happily while the emitted value was the stub `"test"` — the key-presence assertion let a broken value ship for five months with a green suite. For any field whose _content_ is a contract with another system, pin the rendered value (`"firmwareVersion":"3.5.0"`), not just the field name.

### String-search and compile-flag tests (PlatformIO native)

- **Test both sides of a compile-time flag natively by adding a second env, not by mocking headers.** `test_kTransportUsesTls_matches_HPW_USE_TLS_macro` (`libs/firmware-shared/test/test_transport_security/test_transport_security.cpp`) was tautological because `[env:native]` never defined `-DHPW_USE_TLS=1`, so only the `=0` branch ever compiled natively. Fix: added `[env:native_tls]` extending `[env:native]` with only that one flag changed — no ArduinoFake/mock work needed, because `transport_client.h` already guards every device-only header (`WiFiClientSecure`, `gts_root_ca.h`) behind `#ifndef UNIT_TEST`, so those includes never compile in either native env regardless of the flag value. When a header already fences device-only includes behind `#ifndef UNIT_TEST`, reach for a second `[env:native]`-style env that only flips the flag before investing in mock infrastructure.
- Separately, `test_main_cpp_configures_transport_client_before_first_use` had to match literal call-site text (`sendPowerStatus(lastPowerStatus, lastAdcValue)`), not just the function name `sendPowerStatus(` — a bare-name match hits the function's own definition (which precedes `setup()` in `main.cpp`) before the real call site, producing false ordering results. Any future string-search test asserting call _order_ in a file where the callee is also defined must anchor on the actual invocation text, not the declaration/definition.
- **String-search regression guards via raw `.find()` do not distinguish live code from comments.** Sanity-checking `test_main_cpp_configures_transport_client_before_first_use` by commenting out (not deleting) the guarded call still made the test PASS, because `src.find("HomePulse::configureTransportClient(")` matches the substring inside a `//`-commented line too. The guard correctly catches the realistic regression (line deleted or reordered), which is what it was built for; the comment case is a known, accepted limitation any future string-search-based regression test built this way should note rather than assume the check is airtight.

### Firmware: scheduling/eligibility decisions inline in `loop()` are untestable by construction

All three OTA bugs found in one session lived in code no test could reach — two inside `libs/firmware-shared` behind `#ifndef UNIT_TEST`, one inline in `loop()`. The right pattern already existed (`shouldMarkAppValid()`: a pure predicate taking `now`/counters as parameters, natively tested) — it just wasn't applied consistently. Fix was extracting `shouldCheckForOta(nowMs, lastCheckMs, requested, intervalMs)` the same way. Rule of thumb for this firmware: if a condition in `loop()` combines time, state and a flag, it belongs in `ota.cpp`/`debounce.cpp` as a pure function above the `#ifndef UNIT_TEST` fence.

## Extends rules/cts/testing.md — new section: Repo-Interface Mocks

- **`libs/application/.../device/*.spec.ts` mocks for repo interfaces must implement every method exactly.** `IUserDeviceRepository`/`IPowerEventRepository` mocks are typed `jest.Mocked<Interface>`, so a hand-rolled partial mock under-mocks silently until a call site hits the missing method at runtime. `IPowerEventRepository` alone has `findById/findMany/findLatestByDeviceId/create/update/delete/deleteByDeviceId/count`. Copy the mock factory from a sibling spec in the same folder rather than guessing the shape from usage.
- **Entity mocks needing prototype methods must be real instances, not object casts.** `UserDevice.hasAtLeastRole()` is a real prototype method. A test double built as `{...} as UserDevice` type-checks fine but throws "not a function" at runtime when the service under test calls `.hasAtLeastRole(...)` — TS casts don't add missing methods. Construct with `new UserDevice({...})` in specs, not object-literal casts, whenever the entity under mock has behavior methods (not just data).

## Extends rules/cts/testing.md — new section: Compile-Error Regression Tests (`@ts-expect-error`)

This repo's Jest runs via `@swc/jest`, which strips types without checking them, so a `.spec.ts` file's `@ts-expect-error` lines have zero effect at `nx test` runtime — they're only enforced by the `typecheck` Nx target. Writing a "this must be a compile error" regression test (e.g. proving a required field can't be omitted) requires wrapping the offending call in a never-invoked inner function (the `neverRuns()` idiom — see `libs/application/src/lib/services/device/assert-caller-has-role.util.spec.ts`) so Jest doesn't crash on it at runtime; the real verification step is `nx run <project>:typecheck`, not `nx test` — a green Jest run alone does not prove the `@ts-expect-error` is load-bearing.

Two placement gotchas for the directive itself:

- `@ts-expect-error` only suppresses an error on the immediately next source line. A multi-line function call split across lines can put the actual erroring argument on a line other than the one right after the comment, silently failing to suppress it (and, if no error occurs on that exact next line, `tsc` reports `TS2578: Unused '@ts-expect-error' directive'` instead). Collapse the call to one line, or place the directive immediately above the specific line that errors.
- A directive above a multi-line call does not cover a bad argument on a later line. `assert-caller-has-role.util.spec.ts` placed `// @ts-expect-error` above `void assertCallerHasRole(` while the offending argument sat 2 lines lower; `tsc` reports `TS2345` on the argument's own line, so the directive went "unused" (`TS2578`) and the real error surfaced, cascading `application:typecheck` failure into `api:typecheck`. Put `@ts-expect-error` on the line directly above the single expression that errors, inline inside the argument list if needed, never above the wrapping statement.

**Quality-gate note:** `tester(verify)` must run `nx typecheck`, not just the Jest suite — a green Jest run is not a typecheck, since SWC never sees `@ts-expect-error` directives or most other compile-time-only errors.

## Extends rules/cts/testing.md — new section: Reordering Resolve-Calls Can Flip Which Branch a Passing Test Exercises

Fixing `UnlinkDeviceFromUserService`'s target-user-enumeration leak required reordering `execute()` to `resolveDevice()` → `assertCallerHasRole()` → `resolveUser()` (previously `resolveUser` ran first). Two pre-existing specs asserted `toThrow(NotFoundError)` for a missing target user — after the reorder they still passed, but for the wrong reason: without a device mock, they now threw `NotFoundError` from the earlier `resolveDevice()` call instead of `resolveUser()`, and the shared `NotFoundError` class masked the swap. Both specs had to be updated to mock a found device so they keep testing the user-not-found path. Rule: whenever reordering resolve-calls in a service, grep sibling specs for the moved-earlier resolver's happy-path mock being absent in tests that target the moved-later resolver's failure case — a passing `toThrow(SameErrorClass)` is not proof the right branch ran.

## Extends rules/cts/testing.md — new section: Falsy-But-Valid Filter Values Need an Explicit Regression Test

`PrismaPowerEventRepository.buildWhereClause` correctly guards against the falsy-`0`-status filter bug: `status: PowerStatus.OFF` is `0`, so a filter-builder using `if (options.status)` would silently drop it from the Prisma `where` clause (matching all statuses instead of just OFF). The actual check in `power-event.repository.ts` is `options.status !== undefined`, confirmed by reading the source, with an explicit regression test (`power-event.repository.spec.ts`) pinning this — same falsy-filter bug class as the `hasAtLeastRole`/enumeration checks elsewhere in this repo, just in a query-builder instead of an authz check. General repo-spec pattern: any enum/status field whose valid values include a falsy one (`0`, `false`, `''`) needs an explicit filter-builder regression test pinning the falsy-but-valid case.
